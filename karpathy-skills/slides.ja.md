## 4つの原則

| 原則 | 何を防ぐか |
| --- | --- |
| 1) コーディング前の熟考 | 検証なき前提 |
| 2) シンプルさ優先 | 要求外の抽象化 |
| 3) 外科的な変更 | 無関係な「改善」 |
| 4) 目標主導の実行 | **検証なき修正** |

→ 4つ全て試したところ、ベースラインが既にできていることと、そうでないことが分かれました。

## 事例1 — 熟考: 「検証を追加」

**プロンプト:** "この関数に入力検証を追加してください。"

| | A | B |
| --- | --- | --- |
| 追加された検証の数 | 4個 | 3個 |
| 前提の明示 | ✅ | ✅ |
| 仕様外の変更 | 0 | 0 |

> A: 一般的な防御策 — None / 型 / 正数 / 残高
> B: ドメイン的な意味 — 正数 / **同一口座の禁止** / 残高

→ 両方とも合理的。 **違いは僅か — Sonnet 4.6 の基礎力が既に高い。**

---

## 事例2 — シンプルさ: 「TODO関数」

**プロンプト:** "TODO項目をリストに追加する関数を作ってください。"

| | A | B |
| --- | --- | --- |
| 新規クラス | 0 | 0 |
| 総コード行数 | 4 | 4 |
| diff +/- | +3/-0 | +3/-0 |

> 二つの結果がバイト単位で同一:
> `def add_todo(item): todos.append(item)`

→ **違いなし。** 過剰な抽象化のワナは旧モデルの話。現代のモデルは default が minimal。

## 事例3 — 外科的: 「デフォルト値を1行変更」

**プロンプト:** "`color` prop のデフォルトを `\"red\"` に変えてください。"

| | A | B |
| --- | --- | --- |
| 変更行数 | 1 | 1 |
| 無関係な変更 | 0 | 0 |
| 未使用コードの報告 | ❌ | ✅ |

> diff はバイト単位で同一。 **違いは応答のメタ的な振る舞いに:**
> Bだけが「`classnames` import は未使用だが意図的に残した」とユーザーに報告。

→ diff は同じでも、Bは発見を*隠さない*。

## 4つの総合 — 正直な絵 (N=1, Sonnet 4.6)

| タスク | 原則 | A の振る舞い | B の振る舞い | 意味のある違い? |
| --- | --- | --- | --- | --- |
| 1 | 熟考 | 4 検証 | 3 検証 | 僅か |
| 2 | シンプルさ | 3行 | 3行 | **なし** |
| 3 | 外科的 | 1行 | 1行 + 未使用コードの報告 | メタ的な振る舞いだけ |
| 4 | 目標主導 | コード修正のみ | **TDD 4ステップ完了** | **極めて明確** |

→ **Sonnet 4.6 は既に 1~3 をうまく行う。CLAUDE.md の真の効果は *検証を強制する* こと。**

---

## だから、一番大事な一行

> **モデルは基本的に「直した」と終える。**
> **CLAUDE.md が「直したことを証明せよ」に変える。**

- シンプルさ・外科的変更のような自制は既に default
- しかし *検証手順* は明示しないと行わない
- → これが CLAUDE.md 一枚が生む最大の価値
